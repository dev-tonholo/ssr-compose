# 0030. One font resolver per font bundle version, loaded up front in a fixed order

- Status: Accepted on 2026-11-27 by the owner
- Date: 2026-11-27
- Modules: `producer`

## Context

This record replaces [ADR 0029](0029-one-font-resolver-keyed-by-file-fingerprint.md). It states the rule made there for a font's identity as a decision of its own, and changes which sessions share a font resolver. That record gives the memory a resolver per scene costs, and why a font made from bytes needs an identity that names its file: Compose caches such a font by its identity and never by its bytes, so a second file under the same identity, weight and style is measured as the first (probe P46).

ADR 0029 decided on one resolver for the whole process, and left one risk unproven: whether on Linux a glyph missing from one session's font is measured with a font another session registered. The S5 worker found that it is (probe P48 in [research.md R20](../../specs/001-consumer-catalog-bridge/research.md#waking-and-fonts-for-live-sessions-241-242)). Compose registers each font it loads from bytes in its resolver's `TypefaceFontProviderWithFallback`, and Skia uses those fonts as a last resort. With one resolver for both screens, a Roboto line measured 142 px alone, and 92 px after another screen had loaded a font with a glyph that Roboto and the system's fonts lacked. With one resolver per scene it measured 142 px both times. A code point that DejaVu has did not leak, since system fonts win. macOS hides this, because its `.LastResort` font answers every code point, so P46 could not see it. With only the four Roboto files, as before bundle fonts, it cannot happen; it would start when T128 loads bundle fonts.

## Options

- A: one resolver for the whole process, as ADR 0029 decided, with the leak written down. It holds the fewest copies of each font: a live session took 2,778 KB at 3,000 sessions on the reference laptop (P47). But a text's width would depend on which screens ran before it, 142 or 92 px in P48.
- B: one resolver per scene. Nothing leaks between sessions, 142 and 142 px in P48. But each session pays about 708 KB for its own copy: a live session took 3,486 KB at 3,000 sessions on the reference laptop against 2,778 KB with one resolver (P47), and the budget is 2,867 KB.
- C: one resolver per font bundle version that loads all its fonts up front, with one shared by the sessions that use only the bundled Roboto. A session cannot change what a session of another version measures, and within a version the fallback set does not depend on which screens ran. Each version in use pays for its own copy of its fonts and of Roboto, and loads faces that no screen may use.

## Decision

Option C, chosen by the owner on 2026-11-27. A is rejected because a width would depend on which screens ran before, and B because it is over the memory budget.

The producer holds one `FontFamily.Resolver` for each font bundle version, and one more that all sessions with no font bundle share, whose only fonts are the bundled Roboto. `ScreenScene` provides the session's resolver as `LocalFontFamilyResolver` around its screen. A resolver is used only on the scene thread, since Compose's font cache has no lock ([ADR 0021](0021-producer-runs-every-scene-on-one-scene-thread.md)).

A resolver loads all its fonts when it is created. On the scene thread, and before any screen uses it, it calls `FontFamily.Resolver.resolve` once for each face, with that face's family, weight and style, in a fixed order. The faces are the four bundled Roboto faces and, for a version's resolver, every face of that version. The Roboto faces come first, in the order `RobotoFace` lists them. A version's faces follow in the order of `fonts.json`, which is sorted by family, weight and italic ([contracts/font-bundle.md](../../specs/001-consumer-catalog-bridge/contracts/font-bundle.md)). The owner's choice named a version's resolver and a fixed order, such as that of `fonts.json`; this record also settles that the Roboto faces come first and that the resolver for sessions with no font bundle loads the same way, so one rule covers every resolver. No run shows that Skia's pick depends on the order. The set of fonts Skia can fall back to is then fixed by the version alone.

When a version's resolver is created is left to T128. The system-architect recommends creating it for the first session that needs it, so that only versions in use cost memory, and creating it when the producer starts instead if the load time that T128 measures holds other screens too long. This is a recommendation, not part of the decision.

Every font the producer creates from bytes, the bundled Roboto included, takes as its identity `sha256:` and the file's fingerprint: from `fonts.json` for a bundle font, which the producer checks again at start ([contracts/font-bundle.md](../../specs/001-consumer-catalog-bridge/contracts/font-bundle.md)), and computed once at load for Roboto. A key then names exactly one file. This is still needed inside one version, where two families can hold different files under the same weight and style, and two that use the same file share its typeface.

`FontVersionChanged` evicts nothing. The session switches to the resolver and the families of the version it names, the screen recomposes and lays out with them, and the typefaces loaded before stay. One part of this has been neither read in the sources nor run: that a text whose family stays the same, such as one in the bundled Roboto, lays out again with its state kept when only the provided resolver changes. T128's `FontVersionChanged` test has to check it. Keeping typefaces is bounded: the producer loads only the versions it holds at start, so it has at most one resolver for each of them and one for sessions with no font bundle, each holding at most its version's distinct font files and the four Roboto files.

## Consequences

- Good: live sessions on one resolver share one copy of its fonts instead of holding one each. With one resolver for every session, the candidate design came under the 2.8 MB budget on the reference laptop, without headroom for the collector. Sessions with no font bundle still share one that way. The figures, on the laptop (P47) and on a Mac (P43), are in [R20, "4. Constraints and numbers"](../../specs/001-consumer-catalog-bridge/research.md#4-constraints-and-numbers).
- Good: a text's width does not depend on which screens ran first. A session of one version, or with no font bundle, cannot add to the fallback set of another's resolver, and each set is complete before its first screen. The limits below still apply. The tests that prove it come with T128 and have not run.
- Good: the identity rule also fixes the stale font after `FontVersionChanged` inside one scene, which exists with or without sharing.
- Good: the library's own fonts are all registered before a resolver's first screen, so they no longer clear that resolver's shared paragraph cache while screens use it (`FontCache.ensureRegistered`, read in the sources).
- Bad: every face of a version is loaded once for that version, even if no screen uses it, and stays for the life of the process. Each resolver also loads its own copy of the four Roboto faces. Memory grows with each version that gets a resolver, up to the versions held at start; the cost is not measured. The load runs on the scene thread, so every screen waits for it; its time is not measured either. The [contract](../../specs/001-consumer-catalog-bridge/contracts/font-bundle.md#rules) caps each font file at 16 MiB and `fonts.json` at 1 MiB by default, and sets no cap on a version's total.
- Bad: inside one version, a character that a text's font and the system's fonts lack can still be measured with another font of that version. When two of those fonts have it, Skia's pick is native code. T128 needs a test on Linux that a fixed load order gives the same pick on each run; this is not run.
- Bad: a fixed set makes a width repeatable, not proven equal to the device's, which may draw that character with its own system fonts. A resolver per scene has the same gap.
- Bad: server code that builds its own `Font()` still adds it to the fallback set of its session's resolver, for every session that shares it, as long as the process lives. The reader refuses that text, but it reads after layout, so the font is already registered.
- Follow-up: slice S5 in [R20, "Waking and fonts for live sessions"](../../specs/001-consumer-catalog-bridge/research.md#waking-and-fonts-for-live-sessions-241-242), builds only the resolver for sessions with no font bundle, which today is every session. T128 adds one resolver per version and the Linux tests of the fallback between sessions and of the fixed order, and builds bundle fonts with this identity.
