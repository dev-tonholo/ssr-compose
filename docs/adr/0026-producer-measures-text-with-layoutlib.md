# 0026. The producer measures text with layoutlib's Android text classes

- Status: Accepted on 2026-11-27: option L2b, starting with its proofs. Principle III's agreed wording is applied only after the L2b proofs pass, and the owner keeps the final go.
- Date: 2026-11-27
- Modules: `producer`, `core`, `consumer`, `contract-tests`

## Context

The producer lays every screen out and the device draws each node in the box it was sent ([ADR 0015](0015-producer-renders-with-compose-ui-foundation.md)). Desktop Compose on Skia breaks and rounds text lines differently from Android: probe P21 missed the text gate's rule in 10 of 60 texts ([research.md R20](../../specs/001-consumer-catalog-bridge/research.md#text-gate-t123)). [ADR 0025](0025-device-measures-server-text.md) proposed that the device measures each text and reports its sizes.

Then the owner asked how Compose previews match the emulator, which led to layoutlib, the Android renderer Android Studio previews use. A replay of 360 recorded texts per device through layoutlib 16.2.1 (Compose 1.12.1, layoutlib reports API 36) matched every check, including line count, height, box width, line ends, line widths, bottoms, baselines and the ellipsis flag, on API 33 (physical Motorola), API 35 (emulator), API 36 (emulator and physical tablet) and API 37 (emulator and physical Pixel 7 Pro). On API 30 to 32 only line widths differed, in 90 Roboto rows, by at most 0.0156 px. On API 23 to 29, line counts and heights still matched, but Roboto line widths differed by up to 1.73 px, 24 to 28 one-line Roboto boxes were 1 px wider in layoutlib, and API 23 cut 2 ellipsis texts differently. Linux x86_64, in a container under Rosetta on a Mac, gave values byte for byte equal to macOS. Every replay had a control, each text 1 sp larger, that failed. The records are in R20, "Text laid out by layoutlib (#194)".

The owner then asked what it would take to build an engine of our own on the same foundation types, in the way Mosaic runs Compose for terminals, without writing our own composables. It cannot be built next to Compose: foundation's composables emit Compose UI's `LayoutNode`, whose `Owner` is internal, so only a Compose UI platform can host them, and the two we can use are Android (layoutlib) and Skiko (desktop Compose, today's engine); Mosaic avoids this only by writing its own nodes and composables. So an engine of our own comes down to desktop Compose plus a text engine that matches Android. Of four ways to get that text (our own paragraph on Skia, Minikin built from AOSP, the text half of layoutlib, text layout from scratch), only the text half of layoutlib is cheap and proven: called with Compose's settings, the framework's `StaticLayout` and `BoringLayout` matched the device recordings on plain text exactly where L1 did. That design is L2b below. R20, "An engine of our own on Compose foundation (#194)", has the evidence and the estimates.

The owner decided on 2026-11-27: principle III may change to allow layoutlib on the server, only if tests prove it works, keeping real devices and emulators ruled out; API 30 is the line for exact text, older versions stay supported with a documented note; the target is AOSP and Google Android, not other makers' changes; and ADR 0025 is a candidate, not a decision.

## Decision

Accepted on 2026-11-27 by the owner: option L2b, starting with its proofs. The scene stays desktop Compose, laid out without drawing behind the compat seam, and each text's size, line count and baselines come from the framework's `StaticLayout` and `BoringLayout` in layoutlib, called with Compose's Android settings and its copied text rules, through the measure policy of `ScaledBasicText`. An engine of our own is not an option of its own: on a JVM without Android it is desktop Compose, which L2b keeps.

Why: on Linux, the servers' OS, measured on one machine (P38), desktop Compose laid out without drawing updates a screen about four times cheaper than layoutlib (3.1 ms against 11 to 13 ms) and builds a new one more than twice as fast (7.9 ms against 18 to 19 ms). L2b gives the same text as L1 on the rows tested, without Android Compose jars, a second Compose runtime or a class loader split. It keeps the desktop workarounds (the compiler plugin's rewrite of `BasicText`, `ScaledBasicText` and the font scale curve), adds about 1,500 lines of copied Compose text rules, and uses internal Compose API behind the compat seam.

The recorded alternatives, and when each comes back:

- L1, the whole scene in layoutlib: only if the time-boxed L1-1 probe shows both that separate compositions stay well under desktop's per-session memory on the reference laptop and that `RenderSession.measure()`, untimed so far, brings its update close to desktop's 3.1 ms; switching then needs a new decision by the owner. It is the simpler design and may hold a session in less memory (1.8 MB per screen in one composition against desktop's 2.7 MB).
- L2, desktop scene with Android Compose's own `TextMeasurer` inside layoutlib: if L2b's copied rules for line height and ellipsis fail the 360-row replay, since L2 needs no copied rules; it costs a second Compose runtime and a class loader split.
- D, the device measures text ([ADR 0025](0025-device-measures-server-text.md)): if layoutlib's text classes cannot be started without a render session or cannot be shipped to a plain JVM server.

The reference machine. The owner decided on 2026-11-27 that SC-011's 10,000 sessions are measured on the old Linux laptop (Lenovo 82QJ, Ryzen 7 5800H, 8 cores and 16 threads, 31 GB): "If it runs well on the worst, it will run good on the best". The laptop had about 30 GB available before each run. Less the producer's process base (about 0.5 GB for desktop Compose, plus about 0.4 GB once for layoutlib's text classes, a figure from the full bridge, so an upper bound), that leaves about 2.8 MB per session for 10,000 sessions, heap headroom included, for the 50-row screen of these runs. Today's drawn scene holds 14 to 19 MB per session, and C1's layout-only scene about 3.7 MB (793 KB of heap and about 2.3 MB of native memory), so C1 alone is about 0.9 MB per session over the budget. #227 therefore has a target, not only a direction: at most about 2.8 MB resident per live 50-row session on the laptop, which means finding and cutting the native memory per scene (Skia paragraphs, per-scene caches, or the allocator keeping freed memory: resident memory stayed at 21 GB after all 6,100 scenes closed), and T129 measures SC-011 on the laptop with the screen it names.

The first slices, in order, and what each needs before it can merge (R20, "First slices of L2b"):

1. L2b-1, layoutlib's text classes started without Paparazzi and called from several threads, behind `TextEngine`, in a new module that is not published. Needs: its stop rule passing, else D. Changes nothing shipped, so principle III is untouched.
2. L2b-2, Compose's Android text rules copied with their licence headers, and the 360-row replay of every file of API 30 and later as `TextEngine`'s conformance suite. Needs: L2b-1 merged; the replay passing, else L2.
3. C0 then C1 (#227), the compat seam and the layout-only scene, in parallel with the above, since they need no layoutlib. C1 needs C0 merged, the seam's conformance suite, the licence header of the copied `ImageComposeScene`, and its memory test on the laptop against the 2.8 MB budget.
4. The L1-1 probe, time-boxed, in parallel, outside tracked files; it merges nothing and reports to R20.
5. L2b-4, a sample plain JVM server that starts the text classes on Linux from published jars of the unpublished module, built without the Android Gradle plugin. Needs: L2b-1.
6. Only after L2b-1, L2b-2 and L2b-4 pass: principle III's agreed wording is applied, with the owner's go. Then L2b-3 wires `TextEngine` into the measure policy of `ScaledBasicText` and the module is published; L2b-3 cannot merge before the amendment.

The owner decided on 2026-11-27: any internal Compose API the producer needs (`CanvasLayersComposeScene`, `FrameRecomposer`, `PlatformContext`, all `@InternalComposeUiApi`) sits behind one internal compat seam, the only code that opts in, with one implementation for the pinned Compose version and a conformance test suite every implementation must pass; the same applies to layoutlib's text classes behind `TextEngine`. Several Compose versions at once are out of scope until a spec asks for them.

The fix found for M0's failure holds in every option: when a text's overflow is `Ellipsis`, the document carries as `maxLines` the line count its layout ended with, so the device, drawing in the fixed box, keeps the same lines (P27 on the tablet, P28 in layoutlib: 0 mismatches in 2,880 each, measured with `TextMeasurer`; that it equals what `BasicText` draws rests on M0).

## Consequences

- Good: text boxes, line breaks, heights and baselines follow Android's own text classes, exact from API 30 and every value from API 33 on AOSP and Google Android on the rows tested, with no round trip, and a screen shows as soon as the producer laid it out.
- Good: the scene lays out without drawing, about four times cheaper per update and twice as fast per new screen as today's drawn scene on the reference laptop, and drops the raster of 10 to 15 MB per session.
- Good: the proof is a JVM test that replays committed device recordings, so it runs in every build and on Linux CI, and it is `TextEngine`'s conformance suite on every layoutlib upgrade.
- Good: ADR 0015's design stays: the producer still renders with Compose UI foundation on desktop Compose, and the merged work (the plugin's rewrite, `ScaledBasicText`, the font scale curve, the reader) stays in use.
- Bad: the producer depends on layoutlib, its runtime for the server's OS and its resources (about 176 MB) and runs Android framework classes in its process, which needs principle III and its platform constraint changed with the agreed wording, applied only after the proofs pass.
- Bad: about 1,500 lines of Compose's Android text rules are copied and must follow Compose releases by hand, with their licence headers kept; a mistake shows up only in the replay.
- Bad: 10,000 sessions on the reference laptop need about 2.8 MB per session at most; C1 alone gives about 3.7 MB, so #227 must cut native memory per scene, unproven.
- Bad: the scene uses internal Compose API, behind the compat seam, and must pass the seam's conformance suite on every Compose upgrade; supporting several Compose versions at once needs a spec first.
- Bad: devices on API 29 and older can differ by up to 1.73 px in line width and 1 px in box width, and every device draws text the bundled fonts lack with its own fallback fonts. Both are documented, not prevented.
- Bad: whether the framework text classes can start without a render session, and be called from several threads, is unproven until L2b-1.
- Follow-up: #227 (C0 and C1) with the per-session memory target; L2b-1, L2b-2 and L2b-4; the L1-1 probe; the principle III amendment after the proofs; T129 on the reference laptop. ADR 0015 and ADR 0023 stay in force; ADR 0024 stays rejected; ADR 0025 stays as fallback D.
