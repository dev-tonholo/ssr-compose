# 0026. The producer lays screens out in layoutlib

- Status: Proposed
- Date: 2026-11-27
- Modules: `producer`, `compiler-plugin`, `core`, `consumer`, `contract-tests`

## Context

The producer lays every screen out and the device draws each node in the box it was sent ([ADR 0015](0015-producer-renders-with-compose-ui-foundation.md)). Desktop Compose on Skia breaks and rounds text lines differently from Android: probe P21 missed the text gate's rule in 10 of 60 texts ([research.md R20](../../specs/001-consumer-catalog-bridge/research.md#text-gate-t123)). [ADR 0025](0025-device-measures-server-text.md) proposed that the device measures each text and reports its sizes.

Then the owner asked how Compose previews match the emulator, which led to layoutlib, the Android renderer Android Studio previews use. A replay of 360 recorded texts per device through layoutlib 16.2.1 (Compose 1.12.1, layoutlib reports API 36) matched every check, including line count, height, box width, line ends, line widths, bottoms, baselines and the ellipsis flag, on API 33 (physical Motorola), API 35 (emulator), API 36 (emulator and physical tablet) and API 37 (emulator and physical Pixel 7 Pro). On API 30 to 32 only line widths differed, in 90 Roboto rows, by at most 0.0156 px. On API 23 to 29, line counts and heights still matched, but Roboto line widths differed by up to 1.73 px, 24 to 28 one-line Roboto boxes were 1 px wider in layoutlib, and API 23 cut 2 ellipsis texts differently. Linux x86_64, in a container under Rosetta on a Mac, gave values byte for byte equal to macOS. Every replay had a control, each text 1 sp larger, that failed. The records are in R20, "Text laid out by layoutlib (#194)".

The owner then asked what it would take to build an engine of our own on the same foundation types, in the way Mosaic runs Compose for terminals, without writing our own composables. It cannot be built next to Compose: foundation's composables emit Compose UI's `LayoutNode`, whose `Owner` is internal, so only a Compose UI platform can host them, and the two we can use are Android (layoutlib) and Skiko (desktop Compose, today's engine); Mosaic avoids this only by writing its own nodes and composables. So an engine of our own comes down to desktop Compose plus a text engine that matches Android. Of four ways to get that text (our own paragraph on Skia, Minikin built from AOSP, the text half of layoutlib, text layout from scratch), only the text half of layoutlib is cheap and proven: called with Compose's settings, the framework's `StaticLayout` and `BoringLayout` matched the device recordings on plain text exactly where L1 did. That design is L2b below. R20, "An engine of our own on Compose foundation (#194)", has the evidence and the estimates.

The owner decided on 2026-11-27: principle III may change to allow layoutlib on the server, only if tests prove it works, keeping real devices and emulators ruled out; API 30 is the line for exact text, older versions stay supported with a documented note; the target is AOSP and Google Android, not other makers' changes; and ADR 0025 is a candidate, not a decision.

## Decision

Proposed, restated on 2026-11-27 after the same-machine baseline (P38): option L2b, with L1 as the alternative until slice L1-1 measures it, and D as the fallback. An engine of our own is not an option of its own: on a JVM without Android it is desktop Compose, which L2b keeps.

On Linux, the servers' OS, measured on one machine, desktop Compose laid out without drawing updates a screen about four times cheaper than layoutlib (3.1 ms against 11 to 13 ms) and builds a new one more than twice as fast (7.9 ms against 18 to 19 ms). The Mac had shown the opposite for new screens; the laptop decides, because servers run Linux. L2b keeps that scene and takes text from layoutlib's framework classes: the same text as L1 on the rows tested, without Android Compose jars, a second Compose runtime or a class loader split. It keeps the desktop workarounds (the compiler plugin's rewrite of `BasicText`, `ScaledBasicText` and the font scale curve), adds about 1,500 lines of copied Compose text rules, and uses internal Compose API behind the compat seam.

L1 stays the alternative because it is the simpler design, one engine for the whole screen, the same Android Compose the device runs, and because it may hold a live session in less memory: in one composition it used 1.8 MB per screen against desktop's 2.7 MB, while desktop needs about 3.7 MB per session with one layout-only scene each. L1 wins only if L1-1 shows both that separate compositions stay well under 3.7 MB per session and that `RenderSession.measure()`, untimed so far, brings its update close to desktop's. L2 stays the alternative to L2b if L2b's copied rules for line height and ellipsis fail, since Android Compose's own `TextMeasurer` inside layoutlib needs no copied rules. D stays the fallback if layoutlib's text classes cannot be shipped to a plain JVM server or started without a render session.

Four proofs come first, before anything is removed or copied:

1. Done: the desktop baseline on the owner's laptop, the same machine as the layoutlib run (P38).
2. Slices C0 and C1 (#227), needed by L2b and D and good on their own: on the laptop the layout-only scene builds a new screen 2.1 times faster and updates 3 times faster than today's drawn scene and drops its raster, 10 to 15 MB per session. C1 also measures where the remaining 2.3 MB of native memory per scene sits and whether the allocator keeps it after a scene closes (resident memory stayed at 21 GB after 6,100 scenes closed).
3. For L2b: layoutlib's text classes start without Paparazzi (with Paparazzi they needed its render session, P36) and can be called from more than one thread outside `Bridge.getLock()`; all 360 rows of every file of API 30 and later pass with the copied line height, `maxLines` and ellipsis rules; and a plain JVM server, built without the Android Gradle plugin, starts them on Linux from our published jars. If the text classes cannot start without a session, D is next.
4. For L1, a time-boxed probe before it can win: slice L1-1's first test, several screens each in its own composition, with memory per composition and an update through `RenderSession.measure()` timed on the laptop.

SC-011 ("A producer holds 10,000 sessions at once") names no machine. On these numbers 10,000 sessions of 50-row screens need about 40 GB with C1's layout-only scenes, cannot be held on a usual server with today's drawn scenes (140 to 190 GB), and are unknown under L1 until L1-1, about 18 GB if separate compositions cost what one composition does. T129 should state the reference server SC-011 is measured on; that is the owner's call.

The owner decided on 2026-11-27, for every option: any internal Compose API the producer needs (`CanvasLayersComposeScene`, `FrameRecomposer`, `PlatformContext`, all `@InternalComposeUiApi`) sits behind one internal compat seam, the only code that opts in, with one implementation for the pinned Compose version and a conformance test suite every implementation must pass; the same applies to the layoutlib driver if L1 wins. Several Compose versions at once are out of scope until a spec asks for them. The seam, `SceneHost`, comes first in every option (slice C0 of R20, "The compat seam and the layout-only scene"). Under L2b and D the desktop scene stays, so a layout-only scene behind the seam (slice C1) removes the raster surface each `ImageComposeScene` keeps; the coordinator opens an issue for it once the owner agrees.

The fix found for M0's failure holds in every option: when a text's overflow is `Ellipsis`, the document carries as `maxLines` the line count its layout ended with, so the device, drawing in the fixed box, keeps the same lines (P27 on the tablet, P28 in layoutlib: 0 mismatches in 2,880 each, measured with `TextMeasurer`; that it equals what `BasicText` draws rests on M0).

## Consequences

- Good: text boxes, line breaks, heights and baselines are exact from API 30 and every value from API 33, on AOSP and Google Android, with no round trip, and a screen shows as soon as the producer laid it out.
- Good: server code can use text from library modules; the compiler plugin no longer rewrites Compose calls. Material's `Text` becomes possible once Material is in the jar and #224 is settled.
- Good: the proof is a JVM test that replays committed device recordings, so it runs in every build and on Linux CI.
- Bad: the producer depends on about 190 MB of Android artifacts and runs Android framework classes in its process, which needs the constitution's principle III and its platform constraint changed (R20 gives the wording).
- Bad, for L1: on the laptop, one machine for both, an update costs 11 to 13 ms against 3.1 ms for desktop Compose laid out only, and a new screen 18 to 19 ms against 7.9 ms (P38). On the Mac an update cost 6.7 ms with drawing against desktop Compose's 3.2 ms drawn or 1.65 ms laid out only for the same screen, on macOS; layoutlib's `RenderSession.measure()` may skip the drawing but is untimed. Heap per live screen is about the same (722 KB against 765 KB), and native memory per screen was lower in layoutlib on the Mac (about 0.3 MB against 2.2 MB); the laptop baseline settles both on Linux.
- Bad, for L2b and D: with one layout-only scene per session desktop Compose holds about 3.7 MB per session on the laptop, so 10,000 sessions need about 40 GB; C1 looks for where the 2.3 MB of native memory per scene sits.
- Good, for L1 if L1-1 confirms it: 10,000 live screens need about 7 GB of live heap in layoutlib, laid out in one composition, so they fit one 31 GB server on these numbers; what 10,000 separate compositions add is measured by L1-1.
- Bad: layoutlib renders one screen at a time per process, so scale comes from more processes. On the laptop throughput stopped growing at about 140 new screens per second from 4 processes, with every CPU thread busy in runs of 300 screens right after start; the baseline package runs 3,000 screens per process to find the warm rate.
- Good, and true whatever is chosen: desktop Compose as the producer runs it today keeps a raster surface of the screen's size per live screen (10.1 MB at 1080 x 2340, about 14 MB resident each on the Mac), which cannot hold 10,000 sessions on one server. L1 removes it with desktop Compose; under L2b or D the layout-only scene of slice C1, behind the compat seam, removes it.
- Bad: devices on API 29 and older can differ by up to 1.73 px in line width and 1 px in box width, and every device draws text the bundled fonts lack with its own fallback fonts. Both are documented, not prevented.
- Bad: the producer's Android Compose version and the app's should match for text; a different version is not tested.
- Bad: whatever is chosen, the engine's internal API is one implementation of the compat seam, which must pass the seam's conformance suite on every Compose or layoutlib upgrade; supporting several Compose versions at once needs a spec first.
- Bad: merged work becomes unused: the plugin's rewrite (T130), `ScaledBasicText`, the reader's `UnscaledText` checks, the font scale curve in the handshake, and the desktop scene of T122.
- Follow-up: [ADR 0015](0015-producer-renders-with-compose-ui-foundation.md) is replaced by this record if it is accepted; ADR 0023 and ADR 0025 stay as records of the options before it. If L2b is chosen instead, this record is rewritten for it before any slice starts.
